# AR-11: Review sessions open only on a review request made by a writer, one per pull request, and end only through the session's own exit

Written by hand, with `.last_id` moved to 11 in the same commit, for the same
reason as AR-10: architrix's workspace clone of this repo lists only AR-1 to
AR-4. This record replaces AR-10 whole. It restates everything in AR-10 that
still holds, and it names each change: the trigger, who may make it, how a
worker's window ends, and where a clean exit is read.

## Context

AR-10 made two notification reasons a trigger: `review_requested` and
`mention`. It gated a mention by its author's write access, because anyone
can @-mention an account on a public repository.

The gate kept failing review, round after round:

- **#49, round 1 (P0).** A mention was accepted from anyone. A stranger's fork
  PR could open a skip-permissions Opus session that runs its own tooling.
  #49 merged with the write-access gate.
- **#51, closed unmerged.** Three rounds of review on a stricter reading of
  mentions found the next case each time: CRLF, a quadratic scan and a stray
  backtick; then a quoted mention borrowing the quoter's access; then a
  quoted callout and a quoted footnote. Round 3 ended in STOP, and the owner
  chose to drop mentions. None of #51's code reached main.
- **This PR, round 1.** Dropping mention threads by their reason lost real
  requests. GitHub's notification docs say that after an @-mention a thread's
  reason becomes `mention` and stays that way, so a re-request can arrive
  under that reason. The same round found that the web UI lets a PR's author
  re-request a reviewer without any access to the repository (GitHub community
  discussion 151024), and that the daemon never read who made a request.

Four facts from AR-10 still shape the design:

- The reviewer is an outside collaborator on 42 `JesperJurcenoks` and 13
  `disciplin-run-org` repositories, and belongs to no org.
- A freshly started worker writes no model line until it takes a turn. The
  hub reports `idle` before Claude has booted.
- The reviewer's notification threads carry many stale review requests on
  merged pull requests.
- A later round in the same session knows what the previous round found.

Two facts are new, both measured live on 2026-09-11 after #51 closed:

- The hub records a worker's clean exit on its `<worker>-manager` row, which
  posts `/goodbye`. The worker's own row stays `false`
  (`test/fixtures/review-daemon/workers-after-exit.json`).
- A worker's terminal window ran `exec bash` after `claude-tm`, so every
  ended session left an empty shell open.

## Decision

A review request is the only thing that starts or re-sends a round. It
counts only when the owner, or an account with write or admin access, made
it.

- A notification's reason is a hint only. Every unread `PullRequest` thread
  from an allowlisted owner reaches the confirmation step, whatever its
  reason says.
- Confirmation reads GitHub's own records, never a comment:
  - A pull request with no session needs the reviewer in
    `requested_reviewers`, and the newest `review_requested` event must come
    from the owner or a writer.
  - A pull request with a session needs such a request newer than the last
    round.
  - Who asked is the event's `actor`. Access comes from
    `collaborators/<login>/permission`. A 404 is no access. Any other failed
    lookup leaves the thread unread and is asked again on the next poll.
- An @-mention on its own starts nothing. A request made by someone without
  write access is refused and logged to `ignored.jsonl`.

The rest of AR-10 stands unchanged, apart from the last two points below:

- A deterministic Python poller, `bin/jjstack-review-daemon`, run in the
  foreground from the reviewer directory, does the dispatch. No model decides
  what to open, when to send, or when to end.
- GitHub notifications for the reviewer are polled with `If-Modified-Since`.
  A search for pending review requests catches what the feed misses, and it
  goes through the same confirmation. An owner allowlist is checked before
  anything else, and a request on a closed pull request is skipped.
- Each pull request gets one worker, `<dir>-<repo>-pr<N>-tm`, in its own
  terminal window. It is started with `--model opus[1m]` and a session id the
  daemon chooses and keeps. Later rounds go to that worker, and a crash
  resumes that session id.
- A round is sent only to an online, idle worker, after a handshake turn whose
  transcript line shows an Opus model. A wrong model is exited and retried
  once with the full model id, and never reviewed.
- A session ends when its pull request is merged, is closed, or has been idle
  for seven days. The daemon sends `/save-and-exit`. It never uses `tm_stop`
  or a signal, which is AR-2 applied to sessions the daemon owns.
- **Changed from AR-10.** The window runs `"$0" "$@" || exec bash`. A clean
  exit closes it; a failure keeps a shell open so the error can be read.
- **Changed from AR-10.** A clean exit is read from the `<worker>-manager`
  row. An ending without one is reported as an error.
- State is one JSON ledger beside the reviewer's `.env`, written atomically.

## Consequences

- To ask for a round, request or re-request a review on GitHub. Typing
  `@ai-assistant-2026` in a comment does nothing on its own.
- A request made by a pull request's author without write access, including
  a re-request after a writer's first request, opens nothing. So does a
  request after a session has ended. A writer who requests the reviewer on a
  stranger's fork PR still runs that PR's tooling in a skip-permissions
  session. That is a deliberate act by someone the repository trusts, as it
  was in the manual process.
- Each confirmation costs one read of the PR's events and, for someone other
  than the owner, one permission lookup per poll.
- The reviewer's GitHub identity still comes only from the reviewer
  directory's `.env`. The daemon refuses to start when a token in the
  environment could override it, and when the login is not the reviewer.
- Requests from outside the allowlist cost nothing: a local log line, no
  reply, no session.
- Each round costs one extra short turn, the handshake. Pick-up latency is
  bounded by the two-minute poll plus that turn.
- The daemon is a foreground process someone must start. It is not a
  service. Its sessions outlive it, and a restart picks them up from the
  ledger.
- It depends on the hub's REST roster and its `tm_send` tool, on `claude-tm`
  passing unknown flags through to `claude` and on its exit code, and on the
  transcript format Claude Code writes. The frozen specimens under
  `test/fixtures/review-daemon/` pin the roster and transcript shapes as they
  were observed. They cannot see an upstream change, so re-recover them after
  a Claude Code or tubemail upgrade.
- Some dependencies have no specimen at all: the hub routing `/exit` to the
  manager's pty, `claude-tm` passing flags through, and gnome-terminal
  closing a window when its command ends. The last holds while the profile's
  exit action is `close`, as it is on this machine.
- If mentions are wanted again, they should never open a session. A writer's
  mention could, at most, send a question to the pull request's existing
  session.

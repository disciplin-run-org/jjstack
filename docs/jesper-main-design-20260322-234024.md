## Problem Statement

gstack (garrytan/gstack) provides 25+ workflow skills for Claude Code — planning, review, QA, shipping. But it has four structural limitations for power users who want to build on top of it:

1. **Output files are machine-local.** Design docs, CEO plans, review logs, and test plans live in `~/.gstack/projects/` — invisible to collaborators, inaccessible to programs in the repo, and lost when switching machines.

2. **Quality thresholds are fixed.** Plan reviews return 8/10 and stop. Adversarial review gives up after one pass. There's no way to configure iteration depth without editing gstack source files (which get overwritten on update).

3. **No coding skill.** The workflow is Think → Plan → [gap] → Review → Test → Ship. The implementation phase has no orchestration — you exit plan mode and code freehand. There's no skill that reads the approved design doc, loads coding standards, implements methodically, and feeds into review.

4. **No extension mechanism.** You can add new skills alongside gstack, but you can't enhance existing gstack skills without forking. There's no "derived distribution" pattern.

## Demand Evidence

- Jesper has already built 5 custom skills (python-coder, gdocs-writer, medical-translation-qa, mcp-server, create-skill) that extend Claude Code beyond gstack's scope
- After one day with gstack, he identified concrete behavioral changes he wants (higher iteration thresholds, repo-local output, coding workflow)
- gstack has 10K+ GitHub stars and an active ecosystem — power users who want customization exist at scale
- The Claude Code skill ecosystem now has 1000+ templates via the Agent Skills open standard — derived distributions are a natural next step that nobody has built yet

## Status Quo

Today, Jesper manages custom skills as standalone directories scattered in `~/.claude/skills/`. No version tracking, no install script, no cohesive packaging. gstack is an independent git clone that auto-upgrades. The two worlds don't interact — custom skills don't leverage gstack's workflow, and gstack doesn't know about Jesper's coding standards or voice.

When gstack's plan reviews return 8/10, Jesper manually asks Claude to iterate again. When gstack saves design docs, they go to `~/.gstack/projects/` where collaborators can't see them and programs in the repo can't access them.

## Target User & Narrowest Wedge

**Primary user:** Power users of gstack who want higher quality defaults, repo-local output, and the ability to add skills to the gstack workflow without forking.

**Narrowest wedge:** A standalone repo that ships wrapper skills calling gstack skills with enhanced behavior — starting with output redirection to `{repo}/jjstack/` and higher iteration thresholds on plan reviews.

## Constraints

- Must not fork gstack — wrapper/delegation pattern only
- gstack upstream updates must flow cleanly (zero merge conflicts)
- Must work as its own repo (not a subdirectory of personalizations)
- Must be installable by others alongside gstack
- Personal DNA files (Voice DNA, Coding DNA) must be pluggable, not hardcoded

## Premises

1. jjstack is a standalone product/repo — a derived distribution of gstack, not a fork
2. Wrapper skills (jjstack calling gstack via Read tool) are the right pattern for modifying gstack behavior
3. gstack output should be redirectable to `{repo}/jjstack/` for version control and collaboration
4. Personal custom skills (python-coder, gdocs-writer, etc.) stay in the personalizations repo — jjstack is a gstack enhancement layer only
5. The coding phase gap (plan → QA) is a real workflow hole that jjstack should fill (future scope)
6. Personal DNA (voice, coding standards) is a pluggable feature configured via config paths

## Approaches Considered

### Approach A: Wrapper Distribution (CHOSEN)

jjstack is a standalone repo with wrapper skills that delegate to gstack. Each jjstack skill reads its own config, injects context (DNA, thresholds), then invokes the corresponding gstack skill. Output goes to `{repo}/jjstack/`.

**Effort:** M (human: ~1 week / CC: ~2 hours)
**Risk:** Low-Med — delegation mechanism is proven (Claude can read and follow instructions from another file), but iterative looping requires careful prompt engineering to avoid score inflation.

**Pros:**
- Clean separation, zero merge conflicts on gstack updates
- Each wrapper is a thin layer (config + delegation)
- Easy for others to install alongside gstack

**Cons:**
- Wrapper overhead (skill reads wrapper config, then reads gstack skill)
- Can't modify gstack skill behavior mid-execution (only pre/post)
- Runtime coupling to gstack's output paths — if gstack changes where it writes files, wrappers must be updated

### Approach B: Template Override System

jjstack ships modified copies of gstack SKILL.md files with enhanced behavior baked in. A sync script merges upstream gstack changes.

**Effort:** L (human: ~2 weeks / CC: ~4 hours)
**Risk:** Med — merge conflicts on every gstack update. Essentially a fork with extra steps.

### Approach C: Plugin Architecture

jjstack defines a plugin contract — hooks that run before/after gstack skills, config overrides, and output redirectors.

**Effort:** XL (human: ~3 weeks / CC: ~6 hours)
**Risk:** High — requires inventing a plugin API that doesn't exist in gstack.

## Recommended Approach

**Approach A: Wrapper Distribution.** It's the only approach that delivers "derived product, not a fork" without merge conflicts. The wrapper pattern is proven (middleware, decorators, proxies) and the gstack skill format (markdown files) makes delegation straightforward.

### Symlink Override Strategy

gstack installs skills as symlinks in `~/.claude/skills/`:
```
~/.claude/skills/plan-ceo-review → gstack/plan-ceo-review
```

jjstack replaces these symlinks to point to its own wrapper skills instead:
```
~/.claude/skills/plan-ceo-review → jjstack/skills/plan-ceo-review
```

This means `/plan-ceo-review` transparently invokes the jjstack wrapper. The user
types the same command as before — no `jj-` prefix needed. The wrapper delegates
to the original gstack skill by reading it at its real path:
```
~/.claude/skills/gstack/plan-ceo-review/SKILL.md
```

This works because gstack's skill files always exist at their real path under
`~/.claude/skills/gstack/` regardless of which symlinks point where.

**Benefits over the `jj-` prefix approach:**
- Zero behavior change for users — same commands, enhanced behavior
- No need to remember which skills have jjstack wrappers
- Users don't need to choose between `/review` and `/jj-review`
- Uninstall restores the original gstack symlinks — clean rollback

**New skills** (like `jj-code`) that have no gstack equivalent keep the `jj-` prefix
since there's nothing to override.

**Note on personal skills:** Jesper's 5 existing custom skills (python-coder, gdocs-writer,
medical-translation-qa, mcp-server, create-skill) remain in his personalizations repo as
separate installs. They are not part of jjstack's distribution — jjstack is a gstack
enhancement layer, not a personal skill monorepo. Users install jjstack for enhanced gstack
workflows; personal domain-specific skills are a separate concern.

### Wrapper Skill Pattern

A jjstack wrapper skill is a SKILL.md that contains three phases: pre-configure,
delegate, post-enhance. The delegation mechanism uses Claude's `Read` tool to load
the gstack SKILL.md content inline, then follows those instructions within the
wrapper's configured context.

**How delegation works technically:** Claude Code skills are markdown instructions
that Claude reads and follows. A wrapper skill instructs Claude to:
1. Read its own preamble (config, thresholds, DNA)
2. Use the `Read` tool to load the gstack skill file into context
3. Follow the gstack skill instructions, but with overrides from step 1
4. After gstack skill completion, execute post-enhancement steps

This is the same pattern as a developer reading a runbook then following it —
Claude reads the gstack SKILL.md and executes its instructions as part of the
wrapper's larger workflow.

Example wrapper (`plan-ceo-review/SKILL.md`):

```markdown
---
name: plan-ceo-review
description: Enhanced CEO review — iterates to 10/10, saves to repo
---

## Phase 1: Configure (run before delegation)

Read jjstack config to get thresholds:
\`\`\`bash
cat ~/.claude/skills/jjstack/jjstack.config.yaml
\`\`\`

Read DNA files if configured (paths from config above).

**Set these overrides for the gstack skill:**
- Output directory: write design artifacts to `{repo_root}/jjstack/` instead of
  `~/.gstack/projects/$SLUG/`. Use `mkdir -p` to create if needed.
- Quality threshold: note the `min_score` value (default: 10).

## Phase 2: Delegate to gstack

Read and follow the gstack CEO review skill:
\`\`\`bash
cat ~/.claude/skills/gstack/plan-ceo-review/SKILL.md
\`\`\`

Follow ALL instructions in that file, with one modification: when the skill
instructs you to write files to `~/.gstack/projects/$SLUG/`, write them to
`{repo_root}/jjstack/` instead.

## Phase 3: Post-enhancement (run after delegation completes)

**Iterative quality loop:**
After the gstack skill produces its review with a quality score:
1. If score >= configured min_score: DONE. Report final score.
2. If score < min_score AND iterations < max_iterations (default: 3):
   - List each issue the review identified
   - Address each issue in the document
   - Re-run the spec review (dispatch a fresh review subagent)
   - Increment iteration count, return to step 1
3. If max_iterations reached and score still < min_score:
   - Save the document as-is with a "## Reviewer Concerns" section
   - Report: "Reached max iterations (N). Final score: X/10. Remaining
     issues listed in Reviewer Concerns."
   - Do NOT inflate the score to exit the loop.

**Anti-inflation rule:** The re-review must use Claude Code's `Agent` tool to
dispatch a fresh subagent. The subagent prompt must present the document as a
first review — no iteration count, no prior scores, no change history. This
prevents both self-assessment bias and anchoring on previous scores.

**Non-git-repo fallback:** If `git rev-parse --show-toplevel` fails (running
outside a git repo), fall back to `output.location: home` mode and warn:
"Not in a git repo — writing output to ~/.gstack/projects/ instead."

**Wrapper testing note:** Because the output redirect works by instructing Claude
to substitute paths in natural language instructions, each wrapper should be tested
against its specific gstack skill version. If a gstack update changes how a skill
references output paths, the wrapper may need updating.

**Post-delegation verification:** After the gstack skill completes, the wrapper
must verify output landed in the right place:
\`\`\`bash
ls {repo_root}/jjstack/
\`\`\`
If expected output files are missing from `{repo}/jjstack/` but present in
`~/.gstack/projects/$SLUG/`, move them and warn: "Output redirect missed —
moved files from ~/.gstack/projects/ to {repo}/jjstack/. Please report this
so the wrapper can be fixed."

**DNA injection mechanism:** After reading the DNA file content, include it
in the context BEFORE reading the gstack skill. The wrapper instructs Claude:
"The following coding/voice standards apply to ALL output in this session:
[DNA content]. Now read and follow the gstack skill below, applying these
standards to any artifacts you produce."

**README maintenance:** After the gstack skill completes and output is verified,
check the target project's README.md:
1. If no `README.md` exists at `{repo_root}/README.md`: create one that describes
   the project (name, purpose, setup, usage).
2. If `README.md` exists: review whether the changes made in this session affect
   what the README describes. If so, update the relevant sections.
3. Do NOT add a README.md to the jjstack output directory — only to the project root.

This is a **required post-enhancement step** for all wrapper skills. Every jjstack
skill session should leave the project's README.md accurate and current.
\`\`\`
```

### Config System

**Two-tier config with project override:**

1. **Global defaults:** `~/.claude/skills/jjstack/jjstack.config.yaml` (ships with jjstack)
2. **Per-project override:** `{repo_root}/.jjstack.config.yaml` (optional, user-created)

Per-project config merges on top of global — any key set in the project config
overrides the global default. Missing keys fall back to global.

**Config loading order in wrapper skills:**
```bash
# 1. Read global config
cat ~/.claude/skills/jjstack/jjstack.config.yaml
# 2. Check for project override
cat "$(git rev-parse --show-toplevel 2>/dev/null)/.jjstack.config.yaml" 2>/dev/null
```

`jjstack.config.yaml` (global defaults):

```yaml
version: 1                    # config schema version — for future migration

# Quality thresholds
review:
  min_score: 10              # gstack default: 8
  max_iterations: 3          # how many times to loop for higher score
  adversarial_passes: 2      # gstack default: 1

# Output location
output:
  location: repo             # "repo" = {repo}/jjstack/, "home" = ~/.gstack/projects/
  repo_subdir: jjstack       # subdirectory name in repo

# DNA injection (optional — users bring their own)
# Paths are absolute or relative to the project repo root.
dna:
  voice: null                # path to voice DNA file, e.g., ~/ai-personalizations/voice-dna/Voice.md
  coding: null               # path to coding DNA file, e.g., ~/ai-personalizations/coding-dna/Coding.md

# gstack compatibility — update if gstack changes its output paths
gstack_compat:
  output_path: ~/.gstack/projects/$SLUG/   # where gstack writes per-project files
  min_version: "0.11.0.0"                  # minimum gstack version required
```

**Config merge semantics:** Merge is key-level within each top-level section.
Keys not present in the project config retain their global default value.
For example, setting `review.min_score: 8` in the project config preserves
`review.max_iterations: 3` from the global config.

**Known limitation:** Symlink-based install assumes Unix (Linux/macOS).
Windows users would need a different install mechanism (junction points or
copying). This is acceptable for the initial release.

**DNA resolution:** DNA paths in config are the single source of truth. Individual
skills do not embed DNA files — they read the path from config at runtime. This
means users configure DNA once in their global config and all jjstack skills use it.

### Hooks

jjstack ships efficiency hooks that reduce permission friction during Claude Code sessions.

**Auto-approve hook** (`hooks/auto-approve-safe.sh`):

A `PermissionRequest` hook that uses a three-tier risk assessment to auto-approve
safe tool calls without user intervention:

1. **Tier 1 — Read-only tools:** `Read`, `Glob`, `Grep`, `Search`, `WebSearch`,
   `WebFetch` are always approved immediately.
2. **Tier 2 — AI risk classification:** For Bash commands, calls Claude Haiku
   (`claude-haiku-4-5-20251001`) with a 6-second timeout to rate the command as
   `LOW`, `MEDIUM`, or `HIGH` risk. Only `LOW` is auto-approved; `MEDIUM`/`HIGH`
   defer to the normal user permission dialog.
3. **Tier 3 — Fallback heuristic:** If the API key is missing or the call fails,
   a simple regex blocks known-dangerous patterns (`rm -rf`, `sudo`, `git push`,
   `git reset --hard`, `git clean`) and approves everything else.

**Requirements:** `jq`, `curl`, and either `$ANTHROPIC_API_KEY` env var or a key
stored at `~/.claude/anthropic_api_key`.

**Settings config** (injected by `setup` into `~/.claude/settings.json`):
```json
"hooks": {
  "PermissionRequest": [
    {
      "matcher": "",
      "hooks": [
        {
          "type": "command",
          "command": "~/.claude/hooks/auto-approve-safe.sh"
        }
      ]
    }
  ]
}
```

### Install Flow

`setup`:
1. Check gstack is installed at `~/.claude/skills/gstack/` — if not, clone and run gstack's setup automatically
2. Symlink `~/.claude/skills/jjstack` → jjstack repo root
3. For each skill in `skills/` (except `jjstack/` meta-skill):
   - Check if `~/.claude/skills/{skill-name}` already exists
   - If it's a symlink pointing into `gstack/`: **replace it** — repoint to `jjstack/skills/{skill-name}`.
     Save the original target so `uninstall.sh` can restore it.
   - If it's a symlink pointing into `jjstack/`: overwrite (re-install)
   - If it's a symlink pointing elsewhere or a real directory: **warn and skip**.
     Print: "SKIPPED: {skill-name} already exists at {target}. Remove it manually to use jjstack's version."
   - Otherwise: create symlink
4. Save a manifest of replaced symlinks to `~/.claude/skills/jjstack/.install-manifest`
   so `uninstall` knows which gstack symlinks to restore
5. The config file ships in the repo root and is accessible via the symlink — no copy needed.
   If the user wants different global defaults, they edit `jjstack.config.yaml` in the repo directly
6. Install hooks:
   - Create `~/.claude/hooks/` if it doesn't exist
   - Symlink `~/.claude/hooks/auto-approve-safe.sh` → `jjstack/hooks/auto-approve-safe.sh`
   - If `~/.claude/settings.json` doesn't already have a `hooks.PermissionRequest` entry,
     inject the hook config using `jq`. If it already has one, warn and skip.
   - Record hook installation in the manifest for clean uninstall
7. Print: installed skills (with "replaced gstack" note), installed hooks, skipped skills, and usage instructions

`uninstall`:
1. Read `~/.claude/skills/jjstack/.install-manifest` to find which symlinks were replaced
2. For each skill in the manifest:
   - Check if `~/.claude/skills/{skill-name}` is a symlink pointing into jjstack
   - If yes: **restore the original gstack symlink** (e.g., `gstack/{skill-name}`)
   - If no: skip (modified since install)
3. For any jjstack-only skills (like `jj-code`): remove the symlink
4. Remove `~/.claude/skills/jjstack` symlink
5. Remove hooks installed by jjstack:
   - Remove `~/.claude/hooks/auto-approve-safe.sh` symlink (if pointing into jjstack)
   - Remove the `hooks.PermissionRequest` entry from `~/.claude/settings.json` (if it was added by jjstack, per manifest)
6. Do NOT remove config files or output files in project repos — those belong to the user
7. Print: restored gstack skills, removed jjstack-only skills, removed hooks, what was left intact

### Workflow with jjstack

The enhanced workflow is identical to gstack — same commands, enhanced behavior:

```
/office-hours      →  brainstorm, design doc saved to {repo}/jjstack/
/plan-ceo-review   →  strategic review, iterated to 10/10
/plan-eng-review   →  architecture review, iterated to 10/10
/jj-code           →  implement from design doc with coding DNA (NEW — no gstack equivalent)
/review            →  pre-landing review with deeper adversarial passes
/ship              →  ship with jjstack conventions
```

Users don't need to learn new command names. To temporarily bypass jjstack and
use stock gstack behavior, invoke the skill directly via its gstack path.

### jj-code: The Coding Skill (Future Scope)

`jj-code` fills the plan→QA gap in the gstack workflow. This is a **new skill**,
not a wrapper — gstack has no coding skill to delegate to. It keeps the `jj-` prefix
since there's no gstack skill name to override.

**Phase 1: Context Loading**
1. Find the most recent approved design doc in `{repo}/jjstack/` (by timestamp)
2. Read it to understand what needs to be built
3. Load coding DNA from config (`dna.coding` path) for style/standards
4. Read CLAUDE.md for project-specific conventions

**Phase 2: Implementation Planning**
1. Break the design into ordered implementation tasks
2. Present the task list to the user via AskUserQuestion for approval
3. For each task: identify files to create/modify, dependencies, test approach

**Phase 3: Iterative Implementation**
For each approved task:
1. Implement the change (create/edit files)
2. Run pre-commit hooks / linters if configured
3. Run relevant tests
4. If tests fail: fix, re-run (max 3 attempts, then escalate)
5. Commit atomically with descriptive message
6. Move to next task

**Phase 4: Handoff**
1. Summary of what was implemented vs. the design doc
2. List any deviations or open items
3. Suggest `/jj-review` as next step

**Status: FUTURE SCOPE.** This skill requires its own design doc and will be
built after the wrapper pattern is validated with simpler skills like
`/jj-plan-ceo-review`. Listed here to show where it fits in the workflow.

### Error Handling & Failure Modes

**Wrapper delegation fails** (gstack skill not found, gstack updated and moved files):
- Check gstack version: `cat ~/.claude/skills/gstack/VERSION`
- If skill file doesn't exist at expected path: report error with the path tried,
  suggest running `/gstack-upgrade` and re-checking
- Do NOT silently fall back — fail loud so the user knows

**Iterative loop doesn't converge** (score stays below threshold):
- After max_iterations: save document as-is with "## Reviewer Concerns" section
- Report final score honestly — never inflate to exit
- Status: DONE_WITH_CONCERNS

**Output directory conflict** (repo has uncommitted changes in `jjstack/`):
- Check `git status {repo}/jjstack/` before writing
- If dirty: warn user, ask whether to proceed or abort
- Never silently overwrite uncommitted work

**gstack output path changes** (future gstack update moves file locations):
- jjstack.config.yaml includes a `gstack_compat.output_path` field that
  defaults to `~/.gstack/projects/$SLUG/`
- If gstack changes its paths, users update this one field rather than
  editing every wrapper skill
- jjstack release notes should track gstack compatibility

## Resolved Questions

1. **Naming convention:** Symlink override — jjstack wrapper skills use the same names as gstack skills (e.g., `/plan-ceo-review`). The install script replaces gstack symlinks with jjstack symlinks, so the user types the same commands with enhanced behavior. New skills with no gstack equivalent (like `/jj-code`) use the `jj-` prefix. Uninstall restores the original gstack symlinks.
2. **Config location:** Two-tier — global defaults in jjstack repo, optional per-project override via `{repo}/.jjstack.config.yaml`. Project merges on top of global.
3. **DNA pluggability:** Absolute paths in config (`dna.voice`, `dna.coding`). Users set once in global config. No magic discovery — explicit is better than implicit.
4. **Personal skills:** Stay in the personalizations repo, not in jjstack. jjstack is a gstack enhancement layer, not a personal skill monorepo.
